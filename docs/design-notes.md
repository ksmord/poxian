# 设计记录

README 只留结论，这里是实验数据与踩坑过程。所有数字都来自本机实机（magpie 网关 + 真实上游渠道），场景与轮数写在各节。

## 1. 背景：为什么是网关层

这套提示词源自**寒霜破甲工具**——一个 Windows Electron 应用，为每个 AI 编程 Agent 分别安装同一份提示词：改写 `AGENTS.md` / `CLAUDE.md` / `.cursor/rules`、打开记忆开关、甚至二进制补丁替换某个 Agent 内置的系统提示词。代价：

- 每个客户端一套安装脚本；
- 提示词一更新就要重装一遍；
- 官方分发的提示词头部带着作者的版本日志与推广文案；
- 客户端升级会覆盖掉补丁。

poxian 用**一个部件**做同一件事：

- **一处配置**——所有 Agent 本来就走网关，注入点只有一个；
- **位置最强**——写进真正的 `system` 字段，而不是被 Agent 合并到下游的文件；
- **不怕客户端升级**——磁盘上没有任何文件会被覆盖；
- **载荷干净**——v5.2 删除了作者头部污染（版本日志、来源署名、自评广告），正文零改动；
- **随时可逆**——`magpie plugin off poxian` 即关，无残留。

## 2. `replace` 为什么是默认：四组 A/B

问题：请求自带原生 system 时，「前置拼接 = 优先级更高」这条直觉成不成立。

同一模型、同一句诱导、四种写法：

| 组 | 写法 | 结果 |
|---|---|---|
| A | 不注入 | 按原生人格回答 |
| B | `merge` + `prepend` | 仍按原生人格回答 |
| C | `merge` + `append` | 仍按原生人格回答 |
| D | `replace`（system 位只留注入） | 改写身份，按注入人格回答 |

结论：原生 system 还在时，拼接拿不到控制权，位置（前置/追加）都不改变这一点；只有整段替换有效。所以默认 `override: true` + `override_mode: "replace"`。

代价：`replace` 会丢掉 Agent 自己的工具调用规范（Claude Code / Codex 的 system 里带着编辑、搜索、权限的行为约束）。要保住这些规范就显式改 `merge`，接受拿不到控制权。

## 3. 探针：区分「写进去了」和「生效了」

三件事要分开验证：

1. **字节进了请求**：日志 `injected: true` + `payload_sha256`。
2. **模型读到了**：回显探针（`probe_echo`）追加一枚 6 位随机标记，要求回复首行原样吐出。回显到 = 注入确实进了上下文。
3. **读到后认不认**：行为是否真的按提示词走，只有回复内容能回答。

### nonce 不能放 system（0.1.x → 0.2.0 的教训）

0.1.x 把回显标记拼在注入载荷末尾，跟着进 `system`。`system` 是缓存前缀的头，每请求换一枚 nonce，上游逐 token 比对时从 nonce 处断链：

| 版本 | 标记位置 | workbuddy 实测 |
|---|---|---|
| 0.1.x | 载荷末尾（进 system） | 回显 1.3% |
| 0.2.0+ | 末条 user 消息尾部 | 回显 79.4% |

同一份提示词、同一渠道，只挪了标记位置。0.2.0 起默认 `probe_echo_position: "message"`，`payload` 保留但只在调试缓存行为时用。

### 拒答探针

只读回复前 200 字符判是否拒答，不改请求、零 token 成本。单用只能知道「这次拒了」，配回显探针才能区分「没送到」与「送到了不认」。

## 4. 预填（prefill）：让第一个 token 变成续写

做法：请求末尾补一条 assistant，内容就是工件首行（围栏、`1. `、标题），把模型的第一个 token 从「要不要答」挪到「这段怎么接」。会改请求体，默认关。

实机增益（同模型、同题、各 50 次）：

| 路由 | 关闭 | 开启 |
|---|---|---|
| hy4 | 71% | 93% |
| dp4.1f | 71% | 38% |
| k3 系 | 0% | 0% |
| glm | 无增益 | 无增益 |

所以 0.1.9 起不再手写白名单，`prefill_auto` 按「先验 + 该路由滑动统计」自动判断：统计是进程内 EWMA，`n≥4` 才动手，连续拒答会把已开的路由翻成关。

## 5. 性能

**真正的成本不在中间件，在注入体积。** 中间件热路径（2000 次/场景，40 轮对话历史，含完整注入）：

| 场景 | 耗时 |
|---|---|
| `enabled:false` 直接返回 | ~65 µs/req |
| 轻量 V5 注入（8.8K 字） | ~45 µs/req |
| 完整版 v5.2 注入（78.6K 字） | ~36 µs/req |

三个场景的差异在噪声范围。拖慢请求的是 **token 量**，端到端实测（固定 60 轮历史 / 7,572 token，真实网关，`max_tokens:1` 非流式，各 3 次取中位）：

| 场景 | prompt tokens | 中位耗时 | 增量 |
|---|---|---|---|
| 插件关闭 | 7,572 | 1.94 s | — |
| 轻量 V5 | 11,495 | 2.05 s | +0.11 s / +6% |
| 完整版 v5.2 | 28,355 | 2.36 s | +0.42 s / +22% |

每 1K 注入 token 约 +0.02 s prefill，严格线性。所以：

- 默认轻量 V5；要完整蓝图在控制页点「完整版 v5.2」，页面直接标 `~21,073 tok`。
- 只有 Anthropic 系能靠 `cache_control` 摊薄大前缀（约 1/10 价）；OpenAI 兼容渠道没有稳定的跨请求前缀缓存，78.6K 就是每轮全量 prefill。
- 大前缀还吃上下文窗口：agent 更早触发历史压缩，多一轮摘要往返，主观感受比 +0.4 s 更慢。
- 热路径不为全文做字符串拼接：注入文本按版本预计算（`MARKED`），幂等检查逐块 `indexOf` 且命中即返回。

## 6. 相对上游（hangong v1.3.0）的改动

上游 = `YaoGuaiLi/hangong` v1.3.0，MIT。骨架沿用（见 README 的来源表），链路重写。

**构建链**

- 五份 prompt 全部落成独立源文件（`prompts/*.md`）。上游把 4/5 的文本只留在生成的 122KB blob 里，源头丢失、无法维护。
- 构建脚本合并为一个 `scripts/build-prompts.mjs`：唯一输入 `prompts/`，产物 `poxian-prompt.js` + `page/versions.js`。上游两个脚本各写一个文件，且其中一个会删掉 `VERSIONS` 导出，照 README 跑一次就加载失败。
- 版本元数据单一来源（构建脚本 `VERSIONS_META`），页面不再硬编码第二份。

**中间件**

- **过滤器先于握手**：显式 `agents_off` 掉的 agent 不再被握手绕过，也不会被悄悄改模型。
- **握手保留对话历史**：上游把 `messages` 过滤成只剩 user，assistant/tool 全丢；现在只替换 system。
- **握手覆盖全部四协议**：上游只处理 chat/responses，anthropic（Claude Code）和 gemini 发激活词照样灌 78K。
- **幂等**：注入内容首行带 `<!--poxian-->`，同一 body 过两次不会叠成 2×21K。
- **缓存断点默认关**：开启后给注入块加 `cache_control`，大前缀从每请求全价变成一次写入、后续命中；已有 4 个断点时不再争加。订阅代理渠道（WorkBuddy / Trae / SenseNova 等）兼容性不一，叠加 Claw Code 自带 2~3 个断点会踩满上限，部分代理直接拒绝或挂住不返回。上游从不注入 `cache_control`，0.0.3 起默认对齐为 `false`。
- **总闸**：`{"enabled": false}` 一键停用，不必卸载。
- **异常兜底**：内部完整 try/catch，畸形请求不会把异常抛回网关打断链路。
- **原型链防护**：版本 id 查表用 `hasOwnProperty`。上游 `{"prompt":"constructor"}` 会静默关闭注入且不报错。
- **chat 不造双 system**：不假定 system 在第 0 位，扫描首条 system/developer 就地写入。
- **`responses` 支持裸字符串 `input`**：上游只处理数组形式，裸字符串时激活词识别直接失效。
- **gemini 字符串 `systemInstruction` 不被吞**：原文保留为后置块。

**页面与控制台**

- **表单声明式化**：`page/app.js` 顶部 `SCHEMA` 数组声明全部选项，读表单 / 写表单 / 脏检测三处都遍历它。上游三个函数各列一遍字段名，加一个选项要改 4 处（含 HTML），漏一处就是脏检测失灵。
- **脏检测按语义比较**：先归一再逐字段比，不看键序。上游用 `JSON.stringify` 直比，`{"position":"prepend","override":true}` 与 `{"override":true,"position":"prepend"}` 会被判成不同——首次打开就显示「有未保存的修改」。
- **补 `enabled` 与 `cache` 入口**：上游页面没有这两个开关。
