## 一、已完成（改完并通过回归的部分）

全部为**增量开关**。旧配置不写任何新键，行为与 0.1.0 一致。

### 1. 过滤前置（性能）

| 项 | 内容 |
|---|---|
| 文件 | `src/core.mjs`、`poxian.hooks.mjs` |
| 改动 | 新增 `precheck(body, ctx, o)`，把 `skip-body` / `skip-protocol` / 三档过滤从 `handle()` 提出 |
| 效果 | `agents_off` / `models` / 已带标记的请求**不再 `stat` + `read` 一次文件** |
| 兼容 | 日志字段 `src` 在跳过路径写 `null`、`bytes: 0`，字段名不变 |

原顺序是「先 `resolvePrompt()` 再 `filter()`」。被排除的流量白付一次 IO —— 这是规划里 P3「每请求 stat 压力」的真正根因，不是缓存。

### 2. `prompt_path` 目录白名单

| 项 | 内容 |
|---|---|
| 文件 | `src/payload.mjs`、`src/options.mjs`、`src/constants.mjs` |
| 新键 | `prompt_allowlist`，默认 `[]` = 不限制 |
| 判定 | `path.relative()` 判越界；不用 `startsWith()`（`/a/poxian-evil` 能绕 `/a/poxian`） |
| 越界行为 | 不抛异常，回退内置版本，日志 `src=fallback:path-blocked` + `path_blocked: true` |
| 平台 | Windows 盘符/UNC 小写归一 |

### 3. 载荷字节上限

| 项 | 内容 |
|---|---|
| 文件 | `src/payload.mjs` |
| 新键 | `max_payload_bytes`，默认 `0` = 不限制 |
| 超限行为 | 降级回内置版本，日志 `oversize: true` + `requested_bytes` |
| 已知边界 | 降级目标本身也可能超限（内置 `v52` = 83154 B），按「能给的给最好」处理 |

### 4. 日志指纹与轮转

| 项 | 内容 |
|---|---|
| 文件 | `poxian.hooks.mjs`、`src/observe.mjs` |

| 轮转 | `.N-1 → .N` 逐级后移，再 `current → .1` |

### 5. `dry_run`

| 项 | 内容 |
|---|---|
| 文件 | `src/core.mjs` |
| 新键 | `dry_run`，默认 `false` |
| 实现 | `structuredClone` 副本上跑完整流程（含 `handshake`、`adapter.write`），返回 `undefined` |
| 为什么必须克隆 | 适配器的 `write()` 是**原地改** `body.messages`，算的时候原对象已经脏了 |

### 6. `skip_stream`

| 项 | 内容 |
|---|---|
| 文件 | `src/core.mjs` `filter()` |
| 新键 | `skip_stream`，默认 `false` |

| 为什么不用 `body.stream` 一把梭 | Gemini 的流式在 URL 后缀，body 里没有该字段 |

## 二、未实施清单（做不了 / 不该由我定 / 被挡住）

### A. 已从「不做」转为「已实现」

**A1. 会话报文清洗（规划 P0-1）— 已实现，默认关闭**

- 内容：清安全类 system、过滤 assistant 拒绝回执（`enable_message_filter` / `strip_safety_system` / `strip_deny_assistant`）。
- 现状：实现在 `src/filter.mjs`（纯函数），接线在 `src/core.mjs` 的 `applyFilter`。
  `prefilter/` 退化为独立钩子壳，只保留 `hooks.mjs` + `README.md`（**刻意不放 `package.json`**），
  实现复用 `src/filter.mjs`，不再存第二份关键词表。
- 默认：总开关 `false`，旧行为不变；`strip_safety_system` 默认 `true`（但仅在总开关打开时生效）；`strip_deny_assistant` 默认 `false`。
- 实施时踩到的坑，记录备查：
  1. **三种协议不够，是四种** —— 规划只列了 `anthropic` / `chat` / `gemini`，漏了 Responses 的 `body.instructions`。
     `chat` 的 system 位也不是固定 `messages[0]`，要扫第一条 `role=system|developer`。
  2. **删完 assistant 会让角色不交替** —— Anthropic / Gemini 要求 `user`/`assistant` 交替，
     删掉一条拒绝回执后会出现连续两条 user，上游直接 400。所以删完必须合并相邻同角色消息。
     Gemini 例外：`contents` 连续同角色合法，合反而会把两条 `functionCall` 揉成一条，所以单独分支不合并。
  3. **Gemini 的 assistant 叫 `model`**，关键词表照搬会漏。
  4. **插入位置** —— 必须在 `adapter.read()` 之前。放在后面的话，`override=false` 会拿「删之前有没有 system」来判，语义错位。
     但**幂等判定又在清洗之前**：注入内容自身含「禁止」这类关键词，先清洗会把刚注入的那段连同 `MARK` 一起删掉，
     下一轮读到空 system 就重复注入，每轮叠一份。所以顺序是 幂等 → 清洗 → override，三者不能互换。
  5. **关键词黑名单确实会过度匹配**（任何含「禁止」的正常 system 都可能中枪）。
     现状是全有或全无；要精细化得改成声明式规则，这件事仍未做。
  6. **克隆成本** —— 命中才克隆。未命中返回原引用，调用方用 `next !== body` 判「到底改没改」，
     否则每条请求都白付一次 `structuredClone`。
- 覆盖：`test/filter.test.mjs` 26 条 + `cases.json` 新增 7 条端到端（26 → 33）+ `test/chain.test.mjs` 9 条全链路（以 `onRequest` 为入口）。
  前者证明清洗函数本身，后者证明「清洗 + 注入」在真实入口里的顺序契约——纯函数用例不构成对入口接线
  的任何证明，这一层必须单独覆盖。新分支不再零覆盖。

### B. 需要产品决策，我不替你定默认值

**B1. `max_payload_bytes` 的默认值**

- 规划写 `65536`，实测 `prompts/v52.md` = **83154 B**。
- 一旦按 64KB 默认上线，旗舰载荷 `v52` 会被静默降级回 `v5`，等于默认配置下 v52 失效。
- 现状：保留 `0`（不限制），值由你定。建议 `98304`（96KB）。

**B2. `skip_stream` 的默认值**

- 规划写 `true`，但同文档第 4 节要求「所有新增功能默认关闭」—— 自相矛盾。
- 语义上：注入改的是请求体，与响应是否流式无关；默认跳过的实际后果是**所有聊天类流量静默不注入**。
- 现状：默认 `false`（保持旧行为）。真要默认开，需要先确认产品目标是「保护 Agent 会话」还是「全量注入」。

**B3. `handshake_mode: "contains"`**

- 风险：`contains` 命中就调 `replace()`，用 5 行握手指令**整体覆盖**载荷。用户说一句「解释下寒霜是什么」就会触发。
- 没做。若要做，建议 `startsWith` 或「长度 ≤ 32 且包含」，不要裸 `contains`。

**B4. 幂等场景 B 的真正修复**

- 规划只加 `sha256` 到日志，那只是事后对账，**不阻止误判**。
- 若要根治，得在判定时要求「标记 + 载荷前缀指纹」同时命中，或引入 per-request nonce —— 两者都会改变 `skip-mark` 的触发条件，属于语义变更。
- 现状：只加了指纹日志（`payload_sha256`），判定逻辑一字未动。

### C. 受运行环境限制，做不了

**C1. 路径白名单的 `realpath` 加固**

- 当前只做词法比较，符号链接可以绕。
- 不做的原因：本机跑在 PRoot 容器里，`realpath` 结果与宿主路径不一致，加了会误杀合法路径。
- 建议：在非容器部署里再开，用 `fs.realpath` + 二次 `relative` 判定。

**C2. metrics 指标 / 熔断限流（规划 P3）**

- 插件内没有对外出口：magpie 钩子只给 `body` / `ctx`，不暴露 HTTP 端点。
- 现状：只能解析 JSONL。要指标得先确认 magpie 是否支持插件注册路由。

**C3. 控制台页面接实时日志 / payload 在线预览（规划 P2）**

- 页面是零依赖静态产物，桥接 API（`magpie.options.get`）实测在部分版本返回 `undefined`，README 里已记录该不稳定点。
- 要做需要先有稳定的读日志/读运行时状态接口。

**C4. 结构化日志级别（规划 P1）**

- 没做。要先定义级别语义（哪些事件算 `warn`：`fallback:*`？`oversize`？`path_blocked`？），否则只是加个字段没人用。
- 现状：所有事件同一条 JSONL 流，靠 `action` / `src` 前缀区分。

### D. 规划里的技术错误（已避开，未照抄）

| 规划写法 | 问题 | 实际做法 |
|---|---|---|
| `path.dirname(path.resolve(import.meta.url))` | ESM 里 `import.meta.url` 是 `file:///...`，`path.resolve` 当相对路径处理，得到 `/cwd/file:/...` | 未采用；改用 `prompt_allowlist` 方案 |
| `resolved.startsWith(pluginRoot)` | 前缀兄弟目录可绕（`/a/poxian-evil`） | `path.relative()` 判 `..` |
| 限制在插件根目录内 | 直接废掉「外置 md 热加载」这个核心功能 | 白名单可选，默认可读任意路径 |
| `enable_message_filter && !o.dry_run` | 与「dry-run 执行全部 pipeline 计算」自相矛盾 | `dry_run` 走克隆副本，全流程照跑 |

### E. 未排期

- 不兼容 0.1.x 配置，需要迁移脚本 + 重写测试。属于独立排期项，不在本次改动范围。
